# Release process

This document describes Hyperion's release process.

## Overview

Hyperion will use Release Please, conventional commits, GitHub Actions, and
GitHub Releases. Day-to-day development continues on `main`. Release Please
collects releasable changes into a release pull request; merging that pull
request publishes the new version without requiring a developer to create tags
or upload installers manually.

## Version numbers

The current version in `package.json` is the starting point. Release Please
examines conventional commits made since the most recent release and proposes
the largest semantic-versioning change they require:

- `fix:` increments the patch version: `0.2.3` becomes `0.2.4`.
- `feat:` increments the minor version: `0.2.3` becomes `0.3.0`.
- A commit with `!`, such as `feat!:`, or a `BREAKING CHANGE:` footer increments
  the major version: `0.2.3` becomes `1.0.0`.

Other commit types, such as `docs:`, `test:`, and `chore:`, appear in history
but do not cause a release by themselves. If several releasable commits are
pending, only one version is produced and the largest required bump wins.

Release Please opens or updates a release pull request containing the proposed
version in `package.json`, plus generated release notes in `CHANGELOG.md`. This
makes the version and notes reviewable before publication.
The release pull request may be edited when a different version or clearer
notes are needed.

## Publishing a stable release

1. Merge changes into `main` using conventional commit messages.
2. Review the release pull request maintained by Release Please.
3. Merge the release pull request when its version and notes are ready.
4. Release Please creates the matching tag, such as `v0.3.0`, and a GitHub
   Release.
5. A release workflow runs the full quality checks and builds the Electron app
   on macOS, Windows, and Linux runners in parallel.
6. The workflow attaches the signed installers, archives, checksums, and
   Electron update metadata to the draft GitHub Release. A final publication
   job marks it as the latest stable release only after every required build
   succeeds.

The workflow will use the version from the release tag for every package and
will fail if the tag and `package.json` disagree.

## Automatic desktop updates

The packaged desktop app will use `electron-updater` with GitHub Releases as
its update source. Stable builds will check the latest non-prerelease GitHub
Release, compare its version with the installed version, and offer to download
and install the newer signed build. Update manifests and differential-download
metadata will be generated by `electron-builder` and uploaded beside the
installers.

Prereleases such as `v0.3.0-beta.1` may be added later for opt-in testing. They
will be marked as GitHub prereleases and will not be offered to users on the
stable channel. Nightly builds, if introduced, will use a traceable version
such as `0.3.0-nightly.20260830.42`, where the date and GitHub Actions run number
provide the iterator; they will not change how stable versions are calculated.

## Required safeguards

- Pull requests must pass tests, linting, and desktop type checks before merge.
- Stable releases must be built from `main`, never from an unreviewed branch.
- GitHub environments and repository secrets will hold signing and notarization
  credentials.
- The release workflow receives only the minimum permissions it needs, with
  `contents: write` limited to the publication job.
- A failed platform build must leave no partial stable release marked as latest.

The workflow expects `MACOS_CERTIFICATE`, `MACOS_CERTIFICATE_PASSWORD`,
`APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, and `APPLE_TEAM_ID` for macOS signing
and notarization. It expects `WINDOWS_CERTIFICATE` and
`WINDOWS_CERTIFICATE_PASSWORD` for Windows signing. Release builds fail early
when the relevant platform credentials are absent.
